C/C++ size_t and ptrdiff_t

size_t is introduced in C, “which is the unsigned integer type of the result of the sizeof operator” [C99 7.17.2]. Similarly, ptrdiff_t is defined in C, “which is the signed integer type of the result of subtracting two pointers” [C99 7.17.2]. Both of them are typedef (i.e., not a distinct type) in the C header stddef.h.

C++ just inherits these C features (like other standard C libraries) [C++03 18.1]. In C++, both size_t and ptrdiff_t are available in both global and std namespaces (as ::size_t, std::size_t, and ptrdiff_t, std::ptrdiff_t) [C++03 D.5.2].

In C, you may also find in some implementations the special integer types uintptr_t and intptr_t, equivalent to size_t and ptrdiff_t. (In Windows SDK, you can find similar UINT_PTR and INT_PTR.) These types are integer types, but they can safely hold pointers without losing bits. You can perform pointer arithmetic and cast it back to pointer, given that you know what you are doing. C++ does not take these special integer types as its integral parts, and discourages uses of them for good reasons: type safety.

So why do size_t and ptrdiff_t exist? Can’t I just use my favorite unsigned/signed integer types to represent the object size and perform looping, indexing and address/pointer arithmetic? That was the case of K&R C, the predecessor of standardized C. The problem is two-fold: portability and performance.

In the C/C++ world, integer types and pointer are very close relatives, but they differ too. Depending on architecture, integer types may have a different width from a pointer. Commonly, the architecture data model is denoted as IaLbPc, or sometimes IaLbLLdPc. Where I/L/LL/P means integer/long/long long/pointer, and a/b/c/d means with width of the type in bits. For example, if you remember your old Visual C++ 1.x days, DOS huge model was I16L32P32, DOS tiny model was I16L32P16. Win32 is I32L32P32 (i.e., ILP32, flat perfect model). Win32_x64 is I32L32P64 (IL32P64). Now let’s try to use different integer types to represent object size, and see how pointer arithmetic works as an example.

  • unsigned int:
    • DOS_tiny and Win32: Pointer shares the same width with object size, no problem.
    • DOS_huge and Win32_x64: Pointer is wider than object size and pointer arithmetic is broken! For example p+obj_size*10 may not point to the place you want due to silent overflow in multiplication.
  • unsigned long:
    • DOS_huge and Win32: no problem
    • Win32_x64: Pointer is wider and pointer arithmetic is broken.
    • DOS_tiny: object size is wider than pointer, so pointer arithmetic is okay. However, it comes with performance hit, because, in I16L32P16, representing object size with a long would take an extra and unnecessary 16-bit word, costs more in both storage and calculation.

In summary, an explicit integer type (either unsigned int or unsigned long) is not a good choice to represent object size when your code needs to work on different architectures.

So size_t comes to rescue. Simply put, size_t is an unsigned integer type that is wide enough for a pointer, but not too wide to hurt performance. ptrdiff_t is its signed cousin. In most cases, you don’t need to know what they really are, but you focus on their functionalities: representing object size / address difference. The C/C++ implementation makes sure that they are the right integer types good for their purposes.

It is elegant if you plan early and use size_t or ptrdiff_t when writing code that involves sizing, looping, indexing and pointer arithmetic. However, chances are that you have existing code that uses explicit integer types (unsigned/signed int/long) and wants to perform sizing, looping, indexing and pointer arithmetic. In general, there is no safe and easy way to perform the conversion, because in theory you would not know which type is wider considering the code could be ported to different platforms (unless you use boostic compile-time type inference). Given that most modern platforms have non-narrower pointer than various integer types, the preferred solution is to convert these explicit integer types to size_t or ptrdiff_t when mixed code has to happen. Portability in mind, there is no explicit integer type that matches a pointer. If there is, they are size_t and ptrdiff_t anyway.

There was times that some platforms incorrectly defined size_t as a signed integer type, for example GCC prior to 2.4 on some Unix platforms. But this was not standard conformant and GCC quickly fixed it.
