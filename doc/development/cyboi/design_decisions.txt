MIME Types
__________

The CYBOL type constants' names and values have been adapted to follow
the style of the Internet media type / content type that is also
known under the name Multipurpose Internet Mail Extensions (MIME).
These types are managed by the Internet Assigned Numbers Authority (IANA).
See document "Multipurpose Internet Mail Extensions (MIME) Part Two: Media Types":

http://tools.ietf.org/html/rfc2046

Since the MIME standard does not offer media types for certain data,
CYBOL had to invent new languages (media types), e.g. for dates, numbers etc.
This is not meant to pollute the MIME standard, just to fill a gap!
In case IANA adopts these extensions one day -- fine.
If, however, other media type values replacing ours are proposed,
we are open to adapt the CYBOL language specification accordingly.

Arithmetic Operands
___________________

Question:
Is it possible to combine operands of type "integer" and "double" for an arithmetic operation?

Example:
    <!-- This example cuts off decimal places of the resulting number, since integer is used as type. -->
    <node name="divide" channel="inline" encoding="utf-8" language="text/cybol" format="calculate/divide" model="">
        <node name="result" channel="inline" encoding="utf-8" language="text/cybol" format="text/cybol-path" model=".result"/>
        <node name="operand" channel="inline" encoding="utf-8" language="text/cybol" format="number/integer" model="2"/>
    </node>

Answer:
It is NOT possible.
- cyboi uses void* types only for passing parametres around
- a type cast is done before executing an arithmetic operation
- the type could theoretically be read from each argument
- however, both arguments might have different types so that
  cyboi could not decide which operation to use and how to cast
- once, the result might be a double and the operand an integer,
  another time the other way around
- in the end it is the responsibility of the CYBOL developer
  to decide if he wants to work with integer or double values
- a combination of both worlds is not possible, nor necessary
- if needed, there is always the "cast/" operations in cybol

HTML Formatting
_______________

- a cybol constraint "indentation" of type "logicvalue/boolean"
  may be handed over to send/serialise operations that indicates
  whether or not generated html should be formatted
- a formatted file (indented and using more line breaks) is
  approximately three times as big as a "condensed" (non-formatted) one

- if formatting (pretty printing) is wanted, then pre-formatted tags
  might get indented, even though this is not wanted
- therefore, a cybol property "preformatted" of type "logicvalue/boolean"
  may be specified for each html node
- it is excluded from generated html attributes
- actually, it is not a good idea to give format-related properties
  on structure-related tags
- however, THIS IS THE BEST CHOICE, since no-break spaces also have
  to be specified directly
- one functioning alternative would be to filter for <pre> tags
- the problem is that nowadays, preformatting is mostly done via css
  classes whose name may vary, so that they cannot be filtered

Accessing Array Elements
________________________

The following is NOT necessary, since indices may be given to operations like "overwrite" or "add"
* Find solution for accessing single elements of an array from within cybol
--> possibly use "overwrite" operation and specify index as property
--> using a special knowledge path syntax like .settings.buffer[0] is probably NOT possible,
since a knowledge part (and not integer or character value etc.) is to be returned

Question:
Should the knowledge path be extended for accessing single array elements?

Example:
.variables.buffer[0]

Answer:
No, for two reasons.
a) The knowledge path always returns a part, never a primitive like integer etc.
b) The "modify/overwrite" operation has "index" properties, so that
   single elements of an array may be accessed.

Multiple Formats
________________

Question:
Should multiple formats (types) be allowed?
- separated by a pipe character
- as value of the "format" CYBOL attribute
- to be processed in this order, one-by-one in CYBOI

Example:
format="text/plain|UTF-8|tar|gzip"

Answer:
This is NOT necessary.
- there is a "format" attribute in CYBOL, e.g. number/fraction-vulgar
- there is an additional "language" attribute, e.g. text/html
- multiple translations can be handled as separate operations,
  by assigning the result of one translation to a tree node
  which serves as input to another operation
- similar to pipelining in UNIX

Date Time
_________

There are dozens of calendars, historic and in use.
Most of them are based on the position of the sun or/and moon,
others on an era/epoch in which a certain king was ruling.
Neither CYBOI, nor any other system can support them all
with 100 % accuracy, since some epochs of kings can only
be estimated.
Decision: CYBOI will only support the most important calendars.

The modern calendar is the "Gregorian Calendar",
introduced by pope Gregor in the 16th century (1582-10-15).
Decision: Therefore, CYBOI has to offer this date representation.

Another often used calendar is the "Julian Calendar",
introduced by Julius Caesar around 40 B. C.
It was valid until the Gregorian Calendar was introduced.
Decision: CYBOI should additionally support also this date representation.

For computing and many sciences like astronomy etc. it is useful
to have a CONTINUOUS COUNTING of time. This is not the case
with calendars, since they use "leap days" and have inconsistencies,
e.g. the two weeks left out when the Julian was switched to
the Gregorian calendar.
Therefore, a so-called "Julian Day Number" (JDN) exists, which is
something different than the "Julian Calendar". It is the continuous
count of days since the beginning of the Julian Period, starting at
noon on January 1, 4713 BC proleptic Julian calendar, which is
equal to November 24, 4714 BC, in the proleptic Gregorian calendar.
The "Julian Date" (JD) of any instant is the Julian day number for
the preceding noon plus the fraction of the day since that instant.
Julian Dates are expressed as a Julian day number with a decimal
fraction added. For example, The Julian Date for 00:30:00.0
January 1, 2013 is 2456293.520833.
Decision: CYBOI does NOT use the Julian Date, since it is to be
represented as floating point number, which is not very efficient.

Another option is to use a single signed integer number which
increments every second.
This is done so in Unix-like and many other operating systems and
file formats and called "Unix time", or "POSIX time".
It is defined as the number of seconds that have elapsed since
00:00:00 Coordinated Universal Time (UTC), Thursday, 1 January 1970,
NOT counting leap seconds.
Modern Unix time is based on UTC, which counts time using SI seconds,
and breaks up the span of time into days almost always 86400 seconds
long, but due to "leap seconds" occasionally 86401 seconds.
This extra second keeps the days synchronized with the rotation
of the Earth, per Universal Time.
Due to its handling of leap seconds, it is NEITHER a linear
representation of time NOR a true representation of UTC.
When a leap second occurs, so that the UTC day is not exactly
86400 seconds long, a DISCONTINUITY occurs in the Unix time number.
When a leap second is inserted, the Unix time number increases
continuously during the leap second, and then jumps back by 1
at the end of the leap second. This leads to ambiguous Unix
time numbers that can refer either to the instant in the middle
of a leap second, or to the instant one second later.
Decision: CYBOI will use a signed integer number.

Generally, it is necessary to decide whether a time scale is counting:
1 calendar days:
- measurand: time-of-day [mean solar second]
- count of mean solar seconds (which are subdivisions of calendar days)
- determined by astronomy
- example: Julian Date (JD), Coordinated Universal Time (UTC)
- application: civil purposes, modern calendars, most legal systems of time
2 SI seconds:
- measurand: elapsed time interval [SI second]
- following atomic seconds (which are unrelated to calendar days)
- calendar becomes influenceable by politics
- example: Temps Atomique International (TAI)
- application: modern telecommunication, navigation systems
3 other effects:
- just recently, it was found that TAI is not quite accurate
- it was proposed by astronomers to observe effects of pulsars (stars)

UTC is a combination of the first two incommensurate concepts.
It only works fine through the concept of occasional "leap seconds".

Also POSIX tries to be both and as a result it cannot address leap
seconds meaningfully. The Realtime and Advanced Realtime extensions
to POSIX now offer two separate clocks:
http://pubs.opengroup.org/onlinepubs/007904975/basedefs/time.h.html

Decision: CYBOI will use TWO TIMES (separate clocks) internally:
1 Julian Date (JD) based on solar second
2 International Time (TI) or Temps Atomique International (TAI) based on SI second
--> both, JD and TI (or TAI) are determined using the Real Time Clock (RTC) on mainboard
    (Zählerstand Sekunden seit Unix-Epoche 1970)
Remark: auch Betriebssysteme führen eine interne Software-Uhr als Zähler und beziehen nur das Taktsignal via IRQ von der Hardware
Abgleich: erfolgt entweder (1) beim Booten mit Hardware-Uhr oder (2) fortlaufend mit Zeitserver via NTP

A "leap second" as well as "daylight/summer time" are decisions
by some humans to reset all of the clocks to comply with changes.
These two kinds of clock resets are extremely similar, and the
zoneinfo (or tz library) files and POSIX rules already have the
mechanisms for handling both. It now consists of two separate databases:

1 posix: considers a Unix time_t value to be equivalent to the number
of mean solar seconds since 1970-01-01; since 1972-01-01 its value
matches UTC except during leap seconds; every day has 86400 seconds;
for correct time this requires that the system clock be retarded or
reset backward at each leap second; this is the default provided
with most Unix systems, and it is most consistent with POSIX

2 right: considers a Unix time_t value to be equivalent to the count
of seconds actually broadcast in radio time signals since 1970-01-01;
it requires a file of leap seconds to be updated whenever a new one
occurs; for correct time this requires that the system clock
increment monotonically using TAI seconds; despite its name, this is
generally regarded as experimental and inconsistent with POSIX;
this was the branch of code which was briefly used by default in 4.4BSD Unix

There are two time scales which can reasonably be extrapolated back to 1601:
- Universal Time (UT): mean solar second
- Terrestrial Time (TT): SI second

However, UT in all its forms (including GMT) is actually a measure of
time-of-day, which is really the earth rotation angle, and should not
be used anymore, possibly for calculating historic dates, as an exception.

See:
http://en.wikipedia.org/wiki/Unix_Time
http://www.ucolick.org/~sla/leapsecs/timescales.html

Decision: CYBOI will use internal "zoneinfo" maps with information
similar to the "zoneinfo" (or tz library) database files in Unix.
UTC will be treated as timezone distinct from the underlying
operating system time, based on the broadcast time signals.
The only frequent change needed is to place the leap second
information into the internal "zoneinfo" maps, just like timezones.
That way, CYBOI will remain flexible even if broadcast time signals
abandon leap seconds and are based on atomic time only.

The relevant pieces of the POSIX 2008 specification are the definition
of tzset(), and the definition of environment variable TZ.
The only change needed in the POSIX spec is to substitute the
new name of an internationally-approved, uniformly-incrementing,
atomically-regulated broadcast time scale (e.g., "TI", as the
2003 Colloquium in Torino suggested) in place of the current "UTC".
This would allow the underlying system time to increment uniformly while
also allowing the time presented to humans to keep pace with the sun.
It would remove the need for the kernel to handle leap seconds.
It would remove the need for other coding hacks and code complexity
which try to work around the non-uniform timing hiccup which POSIX
compliance currently demands.

See:
http://pubs.opengroup.org/onlinepubs/007904975/basedefs/time.h.html
http://www.ucolick.org/~sla/leapsecs/right+gps.html

Decision: CYBOI will use International Time (TI) in the future,
which is likely to start in year 2022.
It is a candidate for radio broadcast time signals.
TI would be a purely atomic time scale offset from Temps Atomique
International (TAI) by a fixed integer number of seconds.
In order to avoid discontinuities for systems using radio
broadcast time signals the offset would be equal to the
offset of UTC at the instant of switching from UTC to TI.

Allocation
__________

The size of array, item, part is NOT predictable at allocation time,
since it depends on the given type of contained elements.
Therefore, they may NOT be treated like a compound (e.g. datetime, duration)
and special allocation functions have been defined for them.

The size of complex, datetime, duration, fraction, io_entry is fixed,
which is why they may be treated as compounds and do NOT require
special allocation functions.

Q: Should the send/receive operations be held simple, without properties for
serialisation/encoding/compression?

A1: NOT possible. Besides a sender or receiver at least a channel AND language have to be given.

A2: NOT useful. An encoding is neccessary for text (not byte) data.
Requiring the user to encode in cybol before calling "send" is tedious and unconvenient.
The same counts for compression. If channel and language have to be given anyway,
why not specifying the encoding and compression AT ONCE? Both are OPTIONAL anyway and not always needed.

==> Therefore, all of these properties are processed inside send/received.
The encoding must only be considered for text-, not for byte data.

Q: Is the separation of language + format really necessary?
Merge both into one if-else file?
If formats are different in languages, then offer one format per language?

The separation of language + format IS NECESSARY, since html and others
are destination languages and need element/part and simple data types as format.

Encoding
________

Use format "text/ascii" for data that are to be read byte-wise.
Do NOT use format "number/byte", since that will deserialise
text into comma-separated byte values.

Language and Format
___________________

language AND format are both necessary for deserialisation
e.g. a date may be represented differently, depending on the language
- XDT: 31.12.2015 (German format)
- CYBOL: 2015-12-31 (ISO format)
therefore, at first the language is determined, and only
afterwards the corresponding format deserialised

however, the deserialisers for many languages reuse
format deserialisers of the CYBOL language, e.g. for
deserialising integer numbers, since their format is mostly clear

Why is it NOT possible to always call "decode" before "deserialise"?
--> there are languages like HTTP that may contain byte code (e.g. an image)
and deserialising it would destroy data semantics

Why is it NOT possible to always call "deserialise" before "decode"?
--> if the source is given in a text language like XML, then that
has an encoding (e.g. ASCII or UTF-8 with many bytes representing one character)
ignoring the encoding and deserialising byte-by-byte would lead to wrong results

Therefore, an alternative solution considering both problems had to be found.
- text languages first HAVE TO BE decoded, in order to correctly identify characters and then deserialise them
- byte languages do NOT have to be decoded at all and may be deserialised directly

that means deserialiers for text languages have "wchar_t" as source input
and deserialisers for any other (byte) languages have "char" as source input
the output of a deserialiser is always a model

The text "decode" HAS TO BE treated differently from other "extract" byte encodings
(e.g. base64, gzip compression), because its result is always "wchar_t",
whilst other decodings deliver "char".
Therefore, the following chaining is NOT possible:
encoding="utf-8,gzip"
The following, on the other hand, IS POSSIBLE:
encoding="utf-8" compression="tar|gzip|base64"

Stack Memory
____________

Three possible options for using local variables on stack have been evaluated:

1 Manual Creation with Special Operation "memorise/push"

<node name="create_stack_variables" channel="inline" format="memorise/push" model="">
    <node name="break" channel="inline" format="logicvalue/boolean" model="false"/>
    <node name="index" channel="inline" format="number/integer" model="1"/>
    <node name="count" channel="inline" format="number/integer" model="10"/>
    <node name="model" channel="file" format="element/part" model="counter_stack/model.cybol"/>
</node>

Problem: The variables would have to be destroyed manually as well.
If forgotten, they might cause memory leaks.
Also, having to create stack variables manually using a
cybol operation seems complicated and annoying.

2 Part Properties

<node name="logic" channel="file" format="element/part" model="counter_stack/logic.cybol">
    <node name="break" channel="inline" format="logicvalue/boolean" model="false"/>
    <node name="index" channel="inline" format="number/integer" model="1"/>
    <node name="count" channel="inline" format="number/integer" model="10"/>
    <node name="model" channel="file" format="element/part" model="counter_stack/model.cybol"/>
</node>

This is the current solution. It is only usable for compound logic parts
that have been defined beforehand in a cybol logic file. It corresponds
to local variables of a function in classical programming languages.

3 Runtime Initial Values

<node name="execute_logic" channel="inline" format="flow/sequence" model="">
    <node name="model" channel="inline" format="text/cybol-path" model=".app.logic"/>
</node>

Handing over values at runtime. It corresponds to parametre/argument variables
of a function in classical programming languages.

Knowledge Path
______________

MIME Type for cybol knowledge paths: "text/cybol-path"

Symbols:

#   stack memory
.   knowledge memory model (heap)
:   knowledge memory properties (heap)
|   signal memory (message | event queue)
()  part identified by name, which is given as path to a model of format "text/cybol-path", which internally is treated like format "text/plain"
[]  part identified by index, which is given as path to a model of format "number/integer"
{}  part identified by reference, which reads the given path containing another path pointing to the actual model
    OLD: *

Paths using these symbols can be nested.

Memory Examples:

#           stack memory root
.           knowledge memory root model
:           knowledge memory root properties
|           signal memory root

Simple Examples:

#variable_on_stack
.path.to.model
.path.to:property
{.part.containing.path}
    OLD: *.part.containing.path
{{.double_reference.child_node}}
    OLD: **.double_reference.child_node
{#table}.[#row_index].[#column_index]

Part Access Examples:

.(.node.name).child.node
.(.node.(.nested.path.name)).subnode

.[#index_as_integer_on_stack]
.[.path.to.index_as_integer].some.child
.[.x.[.y]]

Complex Examples:

.[.path.to.index_as_integer]
.[{#reference_to_an_index_on_stack}]
    OLD: .[*#reference_to_an_index_on_stack]
:[{{:some_property.subnode}}]
    OLD: :[**:some_property.subnode]
.app.addresses.[#loop_index]
.app.model.[.app.var.dialogue_number].label
{{.part#property.[#index_on_stack].[*.node.index].node.(.node.name.(.nested.path.node)).(**.double_reference.node).link}}
    OLD: **.part#property.[#index_on_stack].[*.node.index].node.(.node.name.(.nested.path.node)).(**.double_reference.node).link

CAUTION! It is NOT permitted to give an integer literal (string) as index, e.g.: .model.[5]

Reasons:

- it was tried to implement this, but it would lead to improper source code
- cybol knowledge paths can be considered to consist of variables as in classical programmes
- variables with prefixes . and : reference heap memory
- variables with the prefix # reference stack memory
- literals are in general forbidden in cybol knowledge paths, all are variable names only
- in all cybol example applications written up to now, the index was used dynamically,
  coming from a variable -- so it does not seem necessary to introduce constant integer literals as index

- integer literals as index could be parsed and converted into a local variable without problem
- but since there is no actual knowledge model behind, the reference to a local variable would have to be returned (forbidden)
- returning the index is important for passing it to the next recursive call of function "deserialise_knowledge"
- of course, one could introduce an additional function argument (parametre) or allocate something additional,
  but this would be improper, blow up source code and make it dirty
- it just does not feel right or necessary

CAUTION! It is NOT permitted to use a path ending with dot or colon, e.g.:
.path.ending.with.model-dot.
.path.ending.with.property-colon:

Reasons:

- it seems tempting to use these for accessing all model nodes or all property nodes, as container
- however, internally to cyboi the "model" item and "properties" ITEM would have to be kept as pointer
- but all of cyboi relies on and processes PART nodes, consisting of items
- therefore, an additional property can be given to cybol container operations,
  in order to identify either the "model" or the "property" hierarchy of a node

Container Operations
____________________

- overwrite/copy: only allow deep copying, NOT shallow --> this avoids multiple pointers to one model and potential troubles with GC
- e.g. primitive models like an integer are always copied by VALUE and models of type "element/part" are always copied DEEP with their whole subtree
- move: it is not very efficient to handle this as: deep copy source model to destination + remove source, in case there is a large sub tree hanging on it

- therefore, as alternative, moving is using SHALLOW copying INSIDE
- add an optional property "move" as boolean to cybol operations "overwrite", "append", "insert"
- when move is true, then use SHALLOW copy, otherwise DEEP copy (default)
- the pointers are references in both cases (already checked), so no problem

- only child nodes are copied/moved, NOT the parent node
- however, the destination node always has to exist already
- then adapt cybol operations in "applicator/modify/"

Comparison
__________

Difference:
- standard comparison: delivers MANY results, one for each element in an array (vector), so that the result is again an array (vector)
- lexicographical comparison: delivers just ONE result

Implementation:
Implement lexicographical comparison in cybop directory called "src/executor/checker/"
ONLY for type "wide_character", since "lexicographical" in effect means "type wide_character".
If integer, double or fraction, a date-time etc. have to be sorted lexicographically,
then sort them INTERNALLY (for date using e.g. cyboi type "datetime") and
only AFTERWARDS, serialise them into type "wide_character" (string)!

Java:
- many programming languages (e.g. Java) return value -1 if lesser, 0 if equal, 1 if greater
- Java knows "equals" with boolean return value AND "compareTo" with int return value
- cyboi should better stick to a standard flag (0 or 1) as return value of the comparison

Operators:
- directory: "executor/comparator/"
- standard comparison operators are implemented: ==, !=, <, >, <=, >=
- others are possible in the future: ~ for "similar" etc.
- the cybol operations are called e.g. "compare/less-or-equal"
- the size of the result array gets extended to the one of the bigger input operand array

Dimension:
- two scalar numbers: direct comparison and just one result
- two vectors: elements get processed one by one and results (0 or 1) are written one by one into a vector (as done e.g. in MATLAB)
- similar to the cybol operation "calculate/add"
- two matrices: not represented by just one node (part), but by a tree of nodes (matrix-row-column or matrix-x-y-z), so that n-dimensional matrices are possible
- CAUTION! matrix comparison has to be implemented in cybol (!), not cyboi, e.g. using a comparison operation operand path like:
    .domain.matrix.[z].[y].[x]
- n dimensions (not only 3, but also more) are possible
- the cybol application developer has to use n nested loops for these n dimensions
- alternatively, n recursive calls using a new stack loop variable for each tree level
- possibly, provide a cybol library offering matrix comparison over n dimensions
- possibly, this library may be used for ANY comparison (?)
- the library always has to be instantiated using "communicate/receive" in memory before usage,
    since it will depend on stack variables, which only exist in the tree after having been instantiated

Lexicographical order:
https://en.wikipedia.org/wiki/Lexicographical_order#Numeral_systems_and_dates
- integer: an integer is larger than another one if either it has more digits (ignoring leading zeroes) or the number of digits is the same and the first digit which differs is larger
- real numbers written in decimal notation:
    - a slightly different variant of the lexicographical order is used
    - the parts on the left of the decimal point are compared as with integer
    - if they are equal, the parts at the right of the decimal point are compared with the lexicographical order
- negative numbers:
    - reverse the order for comparing negative numbers
    - testing the sign in computers takes some time
    - consider two's complement representation for representing signed integers
- string: array of "char" or "wchar_t"; use ASCII and UNICODE, i.e. alphabetical order
- date: represented as Julian Date (JD) integer in cyboi; YYYY-MM-DD etc. get converted into JD integer; thus, a simple number comparison suffices

Hello World!
____________

There are several variants of the "Hello, World!" cybol application
to demonstrate the ease of cybol development and its slim code.
However, it is important to emphasise that it is NOT the task
of a programming language to provide the simplest possible solution
for an output a la "Hello, World!".
Any language following this path is actually a Domain Specific Language (DSL)
for the domain of printing "Hello, World!".

On the contrary, a programming language should be as flexible and
uniform as possible, in other words a General Purpose Language (GPL).
Of course, DSL may ease programming in certain application areas.
But if the aim is to create a schema and language capable of
representing knowledge in general, then a GPL should be the result.
CYBOL is such a GPL and reaches its flexibility by following
the principles of human thinking:
- discrimination (discrete part models)
- composition (parts are containers)
- categorisation (inheritance of part properties)

Input/Output (I/O)
__________________

One of the main issues when writing an application programme
is input/output (i/o). There are different ways to handle it.
Output does not seem to be so problematic, since the programme's
main thread decides when it is going to be sent. Furthermore,
there is the possibility to use special "worker threads".
When it comes to input, then the major problem is the unpredictability of
incoming data or events. Therefore, some solutions are investigated here.

In general, there are two different approaches:
1 Programme is active and i/o passive
2 Programme is passive and i/o active

1 Programme is active and i/o passive

- advantage: easy to understand serial processing

1.1 Blocking call

- synonyms: synchronous communication
- function: blocks the program on just one communication channel
- problem: data arriving on other channels cannot be detected
- example: xcb_wait_for_event, fgetwc

1.2 Non-blocking call

- synonyms: asynchronous communication, busy waiting, spinning, polling, active waiting for state changes
- function: reads multiple channels in an endless loop
- problem: cpu usage (busy waiting)
- problem: does not detect all input if loop is faster than user
- example: xcb_poll_for_event, fgetwc with termios settings ~ICANON; ~ECHO; c_cc[VMIN] = 0; c_cc[VTIME] = 0;

2 Programme is passive and i/o active

- synonyms: hardware interrupt based, event-based, inversion of control (ioc)
- function: interrupt handler or callback function
- advantage: saves system resources (processor time)

2.1 Interrupt request

- function: write interrupt service routines (isr) to handle interrupt requests
- problem: too low-level for cyboi, better leave it to the operating system

2.2 epoll

- advantage: avoids busy waiting
- function: epoll is a linux kernel system call monitoring multiple file descriptors, e.g. terminal, socket
- function: successor of the old solutions: posix select and poll
- function: in windows via WSAAsyncSelect(), WSASelectEvent()
- problem: works only on those channels with file descriptor, not with xcb/xlibs

2.3 libuv of Node.js

- function: handles multiple channels, event-driven asynchronous i/o model
- problem: does not handle graphical windowing system events, e.g. xcb/xlibs
- problem: dependency on external library

2.4 Sensing threads

- function: one thread per channel
- function: detect data and set an internal flag
- problem: main loop needs to check the flag (busy waiting, cpu usage)
- problem: multi-threading differs in operating systems

2.4.1 Asynchronous call and sleep

- problem: thread loop checking for input (busy waiting, cpu usage)

2.4.2 Asynchronous call and pause

- advantage: avoids busy waiting
- function: sigsuspend and system signal to wake up from pause
- problem: the process including its threads is sleeping and cannot detect input
- problem: if running multiple instances of the program, all will be woken up
- problem: system signal specific for operating system

2.4.3 Synchronous call

- function: blocking call of input function within sensing thread
- problem: sensing thread cannot be interrupted from outside
- problem: system signal cannot be used, since only POSIX <pthread.h> provides a function "pthread_kill", but NOT iso c <threads.h>
- problem: alternative flag frequently tested in the thread's endless loop does not work either if using blocking calls of input functions

Conclusion for cyboi:

- mix of solution 1.2 and solution 2.4.3
- one central main thread for signal/event handling with easy to understand serial processing
- it uses a small sleeping time of currently 100 ms
- some channels might (! TEST this yet) be checked asynchronously as in 1.2, e.g. xcb which uses the x window system event queue
- other channels like serial, terminal or socket need a prompt reaction so that several sensing threads are essential
- there is currently no possibility to exit threads from outside, as mentioned in 2.4.3, due to the missing signal function and unchecked flag in blocking function
- as a result, the cybol operation "maintain/shutdown" does currently not work
- this does no harm, however, since the sensing threads that got started in a cybol application may run until that application process exits normally

Example:
The socket channel needs an own sensing thread. If cyboi is acting as server,
then due to the sleep time it is not reacting prompt to client requests.
This can cause already known client sockets stored in a client list
to get "accepted" and redundantly stored in the list a second and
third time etc., instead of just "reading" data from them.

In the future, solution "2.3 libuv of Node.js" might become an option.
But only if asynchronous i/o is provided for all possible i/o channels (gui).
In this case, there would be no more main signal/event handling loop,
but only callback functions reacting to input. Since cyboi processes
all input in an identical manner, these callback functions would have
to call the same identical signal/event handling function (delegation).

Note, that it does not matter how long the microprogramme command pipeline
of the cpu actually takes to process a command. It also does not matter
how long it takes for the cpu to wake up after having been asleep (hlt instruction).
This is because in both cases (main thread or sensing thread),
the cpu processing time is the same and makes no difference
to the event processing in the programme.

Also note, that the scheduler has influence not only by switching
between threads, but also by switching between processes.
Therefore, it would be no advantage to use the main thread
for client data detection and creating a "sensing thread"
seems to be the best solution.

Storing server and client service identification
________________________________________________

Sockets get declared as integer variable in the corresponding cybol
application. However, their initial value is just a placeholder.
Inside cyboi, it gets filled with the correct socket number through
glibc by low-level function calls to the operating system.

A client-side socket (communicating with a server socket) and
a window (communicating with a display server) both get created
using the cybol operation "register/open".

A server-side socket (communicating with many client sockets) and
a display server managing its many windows both get created
using the cybol operation "maintain/startup".

The corresponding timeout gets initialised:
- in function "check_io_accept" of file "accept_io_checker.c"
and reset
- in function "check_io_receive" of file "receive_io_checker.c"

examples/internet/socket_client/app.cybol
examples/internet/socket_server/app.cybol

        This is just a placeholder value.
        Inside cyboi, it gets filled with the correct server socket number,
        which gets created by the operating system through a low-level function call.
    -->
    <node name="server_socket" channel="inline" format="number/integer" model="0"/>

The client list storing client sockets having been accepted by a server
gets allocated together with the corresponding timeout list when
starting up the service:
- in function "maintain_io_allocate" of file "allocate_io_maintainer.c"
- called by function "startup_io" of file "io_starter.c"
- called by function "startup_service" of file "starter.c"

The communication client service identification MAY be given (but does NOT have to)

Receiving Data via Client Socket
________________________________

Data received via socket are stored in a buffer (array).
This happens in an endless loop, since more data than
the buffer can store might be available. Problem:
When there are no further data available, the recv() call blocks.

Solutions:

1 Non-blocking socket mode:

Used on the client side, it causes the recv() function to return
too fast and early, WITHOUT having received the data yet.
Therefore, blocking mode is necessary on the client side and
this solution was NOT chosen.

However, there are some exceptions: Advanced applications like
web browsers handle many connections being the client,
and often do non-blocking connect.

2 Delimiter on application level:

Stream sockets do not delimit messages. All data are an opaque byte stream.
One could implement that on application level, for example:
- a size field in the message header structure
or:
- using a delimiter such as '\n' for single-line text
However, cyboi is to be free of application-level logic.
Therefore, this solution was NOT chosen.

Reference:
https://stackoverflow.com/questions/3053757/read-from-socket

3 Peeking ahead available data:

Microsoft documentation states in several places that MSG_PEEK should
be avoided altogether because it were inefficient and inaccurate.
One is forced to call "recv()" twice.
Therefore, this solution was NOT chosen.
However, it could be a fallback solution if "ioctl" below does not work.

Reference:
https://stackoverflow.com/questions/11266783/recv-with-msg-peek-shows-full-message-but-returns-would-block-normally

4 Using ioctl() to query FIONREAD

This function call will return how many data are available.

The "ioctl" system call is supported by most Unix and Unix-like systems,
including Linux and macOS, though the available request codes
differ from system to system. Microsoft Windows provides a
similar function, named "DeviceIoControl", in its Win32 API.
https://en.wikipedia.org/wiki/Ioctl

#include <sys/ioctl.h>
int ioctl(int fd, unsigned long request, ...);

Example:

int len = 0;
ioctl(sock, FIONREAD, &len);
if (len > 0) {
    len = read(sock, buffer, len);
}

https://www.gnu.org/software/libc/manual/html_node/IOCTLs.html
https://man7.org/linux/man-pages/man2/ioctl.2.html

Handling of windows events versus socket client requests
________________________________________________________

When sensing/receiving a client request via socket, the corresponding
client socket id is returned, so that a response may be sent to it.
This is possible, because all client requests are treated the same way.

However, when working with mutliple different windows, this is not
the case, since each window may have different actions, i.e. react
to events in an own specific way. The window id is received just
like for a socket request. But how to know which content to send?

Therefore, the window id has to be stored and assigned to a specific
variable, e.g. ".gui.main" or ".gui.about_dialogue", right when
starting up (creating) the window in cybol. Only then, responses
to later requests may be sent to the correct window id, by using
comparison (alternative, if-else-else) for identifying the window
that had sent the request (event).

Asynchronous Input/Output
_________________________

* Synchronous Mode: The data are read DIRECTLY from device into the destination item (a given cybol node).
    The cybol operation "stream/read" or "communicate/receive" needs NO special property,
    since synchronous mode is the default.
* Asynchronous Mode: The data are read INDIRECTLY.
    The cybol operation "feel/sense" calls "read" internally and hands over
    the buffer as destination item, which it has retrieved from the client entry.
    In the cybol handler, the cybol operation "stream/read" or "communicate/receive"
    is called and the cybol property "asynchronous" has to be set to TRUE.

Reflexion on event handling:
* Pipe cannot be used, since it might block, when read out to be empty before but an irq was set in a thread only later (filling pipe and setting irq are not atomic)
* Array is good, disadvantage of having to move all entries with each "read+remove"
* IRQ might be set later (filling array and setting irq are not atomic) even though array is empty when main thread was faster reading+removing entry than sensing thread setting irq
--> not a problem, since reading out the array does not block and may just return null, so that NO signal/event is added to the cyboi signal/event memory
* Conclusion: all is fine when working with an array, one for each separate channel; only the irq is sent via pipe
* Hint: APPEND (not overwrite) array elements, so that no input gets lost when input in sensing thread happens faster than processing in main thread

Sensing Threads
_______________

- one sensing thread per channel
- threads are blocking while waiting for message
- set child thread interrupt flag within main thread (called by cybol operation or on cyboi shutdown)
- send some data (such as one byte) from main thread to channel on shutdown, in order to wake up the blocking sensing child thread, so that it can exit itself
- check interrupt flag within child thread and exit thread if flag is set
- use join to let main thread wait until child threads have exited properly

CAUTION! Mind the mutex regions and do NOT call exit thread within them since otherwise,
mutexes may never be reset anymore, if no other thread can enter the locked region

The message length (e.g. http header entry "Content-Length:") or
message end (e.g. <cr>+<lf>) gets detected twice:
- in sensor to be able to set the irq pipe
- in reader to be able to split several messages, since more than one might have been received and stored in the buffer

See for example files: "completeness_check_socket_sensor.c", "message_socket_sensor.c", "server_socket_reader.c"

Source buffer data stemming from sensor are removed in stream readers of
all channels to avoid processing the same data again and again.

Blocking and Non-blocking Mode
______________________________

CAUTION! Some other chapters on Input/Output (I/O) and socket communication further above are OUTDATED!

A cybol property "blocking" with boolean value is not provided.
In cyboi, all communication is BLOCKING.

The server (display, socket) senses input in a child thread.
The client sends data waiting for a server response.

Trying to make the socket client "non-blocking" resulted
in error "EWOULDBLOCK" when reading/writing.

Open questions:

1 In the future, something like "worker threads" have to be implemented,
  so that a client may send data in standard blocking mode and
  continue with other work right away.

2 Is it really necessary to provide blocking terminal communication

Beispiel lexikalisch im Gegensatz zu dynamisch
______________________________________________

Quelle:

AUSZUG aus dem Wikipedia-Artikel "Variable (Programmierung)":
https://de.wikipedia.org/wiki/Variable_(Programmierung)#Beispiel_lexikalisch_im_Gegensatz_zu_dynamisch

Inhalt:

C++ und C verwenden lexikalische (statische) Gültigkeitsbereiche:

int x = 0;
int f() { return x; }
int g() { int x = 1; return f(); } /* g() => 0 */

Im obigen Programmfragment ergibt g() immer 0 (den Wert der globalen Variablen x,
nicht den Wert der lokalen Variablen x in g()). Dies ist so, weil in f() immer nur
das globale x sichtbar ist.

In Perl können lokale Variablen lexikalisch (statisch) mit dem Schlüsselwort my oder
dynamisch mit dem irreführenden Schlüsselwort local deklariert werden
Das folgende Beispiel entspricht dem obigen in C:

$x = 0;
sub f { return $x; }
sub g { my $x = 1; return f(); }
print g()."\n";

Dieses Beispiel benutzt my, um $x in g() einen lexikalischen (statischen) Sichtbarkeitsbereich zu geben.
Daher wird g() immer 0 ergeben. f() kann g()’s $x nicht sehen, obwohl dies zum Zeitpunkt,
zu dem f() aufgerufen wird, noch existiert.

$x = 0;
sub f { return $x; }
sub g { local $x = 1; return f(); }
print g()."\n";

Dieses Beispiel benutzt local, um $x in g() einen dynamischen Sichtbarkeitsbereich zu geben.
Somit kann f() den lokal, in g(), geltenden Wert von $x verwenden und g() liefert den Wert 1.

In der Praxis sollte man in der Regel für Variablen in Perl "my" verwenden.

CYBOP:

CYBOL verwendet die DYNAMISCHE Deklaration lokaler Variablen.
Sie werden als "property" definiert und auf den Stack-Speicher gelegt.
Wenn eine äußere Funktion Variablen definiert, so sind diese auch für
aufgerufene Unter- bzw. Kindfunktionen sichtbar und verwendbar.

Beispiel:

    <node name="rows" channel="file" format="element/part" model="application/presence/logic/create/choices/rows.cybol">
        <node name="break" channel="inline" format="logicvalue/boolean" model="false"/>
        <node name="index" channel="inline" format="number/integer" model="0"/>
        <node name="count" channel="inline" format="number/integer" model="0"/>
        <node name="model" channel="inline" format="text/cybol-path" model=".logic.create.choices.row"/>
    </node>

Super
_____

Inheritance (categorisation) is currently (2023-01-30) NOT used in CYBOL.
The current approach is "prototype programming" based on COMPOSITION.
Models given in CYBOL files may be created/instantiated/allocated
as tree node and its property values adapted as needed.

If inheritance becomes necessary anyway one day, then it might be
implemented similar to the "prototype chain" in ECMA/JavaScript.

Earlier trials in CYBOL used a property node called "super" or "class"
for this, but not any longer.

Problem 1: Common super model properties

When assigning a "super" property as cybol-path, it may be evaluated
at runtime and the "super" model and its properties be accessed.
However, a gui component, for example, needs its VERY OWN properties
like "position" and "size" which have to get manipulated and changed.
It therefore does NOT help to access the position and size of
a super model that is common to many gui components.

A super category might make sense for gui components, for example.
This has to be figured out still when writing the gui serialiser.
The models belong to just ONE dimension like: TUI, GUI, WUI with
common properties, so the upper-most category for a tui model may be one
that provides ALL essential properties like "shape", "border", "background" etc.

Problem 2: Path overwritten with primitive value

A property might be given as path to a common value, for example a system colour:

    <node name="background" channel="inline" format="text/cybol-path" model=".app.settings.system_background"/>

In such cases, it must NOT be overwritten directly. However, sometimes
it IS necessary to overwrite a colour value, for example when selecting
(focussing) a menu item:

    <node name="focus_item" channel="inline" format="modify/overwrite" model="">
        <node name="destination" channel="inline" format="text/cybol-path" model=".app.tui.item"/>
        <node name="source" channel="inline" format="knowledge" model=".app.settings.focus-colour"/>
    </node>

In this case, the cybol-path would be OVERWRITTEN with a terminal colour value.
Therefore, using a cybol-path is NOT recommended, since each gui component
should have its very own property values.

Recursion via Stack Variables
_____________________________

When reading a data format with hierarchical elements of whom is not known,
how deep the hierarchy will be, then RECURSION is definitely necessary.

Even though the final solution in CYBOI is quite easy to use,
the way finding it was not. It took me two weeks of intensive thinking.

Here are some reflexions on the topic:

1 Format "number/pointer"

- storing pointer directly in CYBOI
- neither possible nor wanted in CYBOL
- advantage that direct manipulation of memory is not possible
- access happens through tree paths only
- other solution would not be possible, since primitive operations expect simple tree paths as parametre
--> direct pointer storeage not possible

2 Changing Tree Path

- inefficient since "modify/append" has to be called frequently
- only one index is available in stack, but does not match for each subnode
- example: .test.a[x].b[y].c[z]
- all different indices would have to be stored on stack for each tree level
- but the number of levels is unpredictable with recursion
- therefore, tree path manipulation does not suffice
--> storage of an "element/part" pointer on stack is inevitable

3 Accessing a Part Pointer via Tree Path

- given as property being stored as stack variable
- using names such as "parent" or "super" or "ref"
- or via tree path using separator "@"
--> access via classical tree path without new separator preferred

4 Accessing a Part Pointer via "modify/overwrite"

<node name="record" channel="file" format="element/part" model="xdt2html/logic/translate/record.cybol">
    <!-- The parent node for recursion of compound fields -->
    <node name="parent" channel="inline" format="element/part" model=""/>
</node>

<!-- Stacking -->
<node name="store_record_as_parent" channel="inline" format="modify/overwrite" model="">
    <node name="destination" channel="inline" format="text/cybol-path" model="#parent"/>
    <node name="source" channel="inline" format="text/cybol-path" model=".xdt"/>
    <node name="source_index" channel="inline" format="text/cybol-path" model="#record_index"/>
    <!-- Copy only one pointer. -->
    <node name="count" channel="inline" format="number/integer" model="1"/>
    <!-- CAUTION! The "true" means shallow copy for now. Delete this later, since "true" should be made the DEFAULT in cyboi. -->
    <node name="move" channel="inline" format="logicvalue/boolean" model="true"/>
</node>

- somewhat complicated due to necessary call of "modify/overwrite" in sub function
- works fine for copying the pointer reference to a part
- however, not usable, since the "parent" stack variable gets overwritten each time
- after having finished the sub function, the old parent value is not available anymore and lost
- therefore, following elements in a list can not be processed anymore

5 Introduce new format "element/reference"

<node name="loop_fields" channel="inline" format="text/cybol-path" model=".logic.translate.fields">
    <node name="parent" channel="inline" format="element/reference" model="#parent.[.stack_pointer_index].[#record_index]"/>
</node>

- does not work with format "text/cybol-path" since that is treated and stored on stack as string
- when format "element/reference" is found, then the path gets resolved at runtime in handler
- references that element via tree path which is to become the new parent node
- stores internal pointer reference (and not just path) to a part as shallow copy on stack memory
--> best solution

6 Tree Path Syntax Extension for Stack Variable Access

- example:
    <node name="parent" channel="inline" format="element/reference" model="#parent.[.stack_pointer_index].[#record_index]"/>
- the stack variable "parent" stores a pointer as reference to its first child part
- therefore, an index like [.stack_pointer_index] has to be given, which is set to zero by default
- this is somewhat tedious and an easier solution desirable
- perhaps the knowledge tree path syntax could be extended
- for example by a separator "@" to access the first child automatically
- example:
    <node name="parent" channel="inline" format="element/reference" model="#parent@[#record_index]"/>
- the knowledge path deserialiser would have to be adapted for this
--> currently not implemented, since it would blow up and complicate the tree path syntax

7 Separate Pointer Pool Memory

- heap for global knowledge tree; stack as buffer for local parametres of compound operations
- question: introduce a separate reference memory for pointers to parts (objects)?
- storing all direct pointers in parallel to stack memory
- complicated and not desirable
--> better use existing stack memory

8 Hierarchy of Property Values

- in this order: 1 super, 2 local, 3 cybol-path
- super is not useful for operations
- local parametres and cybol-path properties can be treated the same
--> nothing special needed, just use standard properties

Header Files
____________

In early versions when consisting of just one executable file without usage
of libraries, cyboi did NOT use header files, for the following reasons:

1 Effort: There are hundreds of implementation files, one per function.
2 Dependencies: They are straightforward and clear between implementation files.
3 Simplicity: Other languages like java do not use header files either.

Meanwhile, header files declaring function signatures ARE USED in cyboi,
since working with libraries makes it necessary, for two reasons:

- including source files would blow up binary library file size
- libraries would include each other's source code
  which is against the idea of a library

On the way of this development towards using libraries and header files,
it became necessary to SUM UP all relevant source files via include.

The instruction "add_library" of file "CMakeLists.txt" expects a list
of all relevant source files to be added to the library.
However, it is important to specify only ONE source file since otherwise,
the following error will occur in almost all cases:

/usr/bin/ld: CMakeFiles/[library].dir/[file].c.o: in function `[function]':
[file].c:(.text+0xe53a): multiple definition of `[function]'; CMakeFiles/[library].dir/[file].c.o:[file].c:(.text+0xf274): first defined here

The reason is that each source file added via "add_library" is treated
SEPARATELY when it comes to adding its include files. But since cyboi did,
in the past, NOT use header files (*.h) and included source files (*.c)
DIRECTLY instead, the above "multiple definition" error occured.

In order to avoid this, ONE special source file has been created for EACH
library, whose sole sense is to SUM UP all relevant source files via include.

Matrix, Vector/Array, Addition with many operands
_________________________________________________

- Mixing of minuend and subtrahends in one array is NOT good and not done in cybol, for example in clojure (functional programming): (- 24 8 6)
- Instead, DIFFERENT cybol properties are used, one for minuend (result) and another for subtrahend (operand)

- a matrix can be resembled in cybol by its tree structure, just like a table in html
- cybol variables can be ONE-dimensional arrays only

- an addition in cybol does always add vectors/arrays by default
- example: "1,2,3" + "2,2,2" = "3,4,5"

Functional Programming
______________________

Allgemeine Gedanken:

Im Grunde handelt es sich bei den Besonderheiten der funktionalen Programmierung
nur um Funktionen, die auf Containern/Collections arbeiten.
Sie können per Schleife ohne Rekursion nachgebildet werden, da effizienter.
Siehe cybol Operation "flow/loop-each"!

In der funktionalen Programmiersprache Clojure gibt es drei wichtige Funktionen:
- map: anwenden einer Funktion auf einzelne Elemente
- reduce: kombinieren von vorherigen Ergebnissen und Elementen
- filter: auswählen gewünschter Elemente

Das Verhalten der ersten beiden Funktionen "map" und "reduce" kann in CYBOL
mittels einer "flow/loop-each"-Schleife nachgebildet werden.
Zum Nachbauen von "filter" wird es in Zukunft einige "select/" Funktionen geben.

Primitive CYBOL-Operationen akzeptieren nur die vordefinierten Eigenschaften
(properties), auf welche über den Namen zugegriffen wird.

Der Versuch, die Syntax funktionaler Sprachen nachzubauen, würde es nötig machen,
mehrere Operanden als Liste entgegenzunehmen und über einen Index statt Namen
auf sie zuzugreifen. Dies würde den CYBOI-Quelltext verkomplizieren und
ist weder sinnvoll oder nötig.
Die meisten CYBOL-Operationen benötigen keine Parameterübergabe per Index,
da sie nicht mit Listen arbeiten, zum Beispiel
"maintain/startup" oder "activate/enable" oder "flow/loop".

Implementierung in CYBOI:

Zunächst wurde versucht, eigene Funktionen "modify/map" und "modify/reduce"
zu schreiben. Dies wurde später verworfen, da über "flow/loop-each" beide
Verhalten nachgebaut werden können.

Eine weitere Fragestellung war die Implementierung des Elementzugriffs
für eine Liste aus der aufgerufenen Funktion heraus.
Ein direkter Zugriff auf Speicher-Zeiger ist im CYBOL-Code nicht erlaubt.
Deren Verwendung wäre unsauber, würde zu Sicherheitsrisiken führen und
Speicherfehler durch gewollte oder ungewollte Manipulation provozieren.
Also sind Zeiger in CYBOL nicht referenzierbar und es existiert kein
Datentyp dafür.
Alternativ dazu kann der Element-Index verwendet werden, um via
knowledge path auf das aktuelle Element zuzugreifen.
Dies kann bei Verwendung der "flow/loop-each" so gemacht werden.

Direkte Zeiger werden in CYBOL aus folgenden Gründen NICHT verwendet:
- cybol soll frei davon bleiben
- aus Sicherheitsgründen
- schwierig umzusetzen: ein Test mit Addition zählte den Zeiger hoch, da er nicht dereferenziert war
- also müsste der Zeiger in cybol umständlich dereferenziert werden
- ist alles nicht nötig, wenn man den Index übergibt
- lokale Variablen können optional als Stack-Variablen verwendet werden

Primitive CYBOL-Operationen wie "calculate/add" brauchen nicht funktional verwendet zu werden:
- sie können durch eine eigene cybol Datei gekapselt und so verwendet werden
- Parameter brauchen nicht als Liste angegeben zu werden, denn Properties haben einen Namen
- die Art und Weise der Verarbeitung der Properties im "applicator" müsste sonst angepasst werden,
    so dass sie nicht nur namensbasiert, sondern auch nach der Reihenfolge verarbeitet werden könnten
- es sind nur einige wenige cybol Operationen wie calculate/add, die funktional
    im Stil von "reduce" verwendet werden könnten, weswegen der Aufwand
    zur Anpassung der Verarbeitung der Properties in Reihenfolge nicht lohnt

Path or Part
____________

CAUTION! There is a DIFFERENCE in how a part containing a cybol path as model is retrieved:

1 Leave cybol path as is

- used in function "copy_array_forward" identifying a tree node by index
- used in function "get_name_array" identifying a tree node by name
- treats cybol path as pure string
- returns the properties of this cybol path part itself

2 Resolve cybol path

- used in functions "get_part_name", "get_part_knowledge", "deserialise_knowledge" identifying a tree node by path
- resolves the cybol path diving deep into the tree hierarchy
- returns the properties of the tree node that the cybol path points to

Therefore, different functions are used depending on the purpose:

- copy_array_forward: get part as compound element to be handed over to "handle", done in "handle_element" and "read_signal"
- get_name_array: get part as model to be handed over to "handle", done in sequence/loop/branch
- get_part_name: retrieve the properties belonging to a cybol operation, done in most applicator functions
